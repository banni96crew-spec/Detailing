## Правила достоверности

- **CONFIRMED** — факт непосредственно подтверждён сообщением пользователя, сохранённым выводом команды, журналом, файлом или коммитом.
- **INFERRED** — вывод согласуется с несколькими подтверждёнными фактами, но прямого доказательства причины нет.
- **UNKNOWN** — доступных данных недостаточно.
- `VERIFIED` — исправление подтверждено последующим результатом.
- `PARTIALLY_VERIFIED` — часть цепочки исправлена или применён обходной путь, но первопричина либо конечный результат подтверждены не полностью.
- `PROPOSED` — профилактика или исправление выведены из текущего состояния и документации, но в этой истории не применялись.
- `UNRESOLVED` — подтверждения исправления нет.

Предлагаемые ниже проверки и команды помечены как профилактические. Они не выдаются за исторически выполненные действия.

## 1. Общая информация

### 1.1. Характеристика приложения

**CONFIRMED:** приложение — многопользовательская платформа записи в детейлинг-студию. Публичная часть открывается по пути `/s/:slug/`; для исследованной студии использовался slug `graphite`. В приложении есть выбор услуги и времени, создание и отмена записи, просмотр своей записи, выгрузка события `.ics`, браузерные push-уведомления и кабинет владельца.

**CONFIRMED:** приложение поддерживает два режима:

- реальный режим: данные читаются и изменяются через Supabase;
- демонстрационный режим: данные хранятся в `localStorage` конкретного браузера.

### 1.3. Архитектура развёртывания

```text
Браузер
  -> Vercel: статическая сборка Vite и маршруты /s/:slug/*
  -> Supabase REST/RPC: public_tenant_bootstrap и данные каталога
  -> Supabase Edge Function public-api: слоты, записи, push-подписки
  -> Supabase Edge Function owner-api: операции владельца
  -> Supabase Edge Function assistant: помощник
  -> Supabase Edge Function notification-dispatch: отправка уведомлений
  -> PostgreSQL/Storage/Auth: постоянные данные, файлы, пользователи
```

Публикация студии выполняется отдельным сценарием `scripts/tenant-publish.ts`; применение миграций и развёртывание функций само по себе студию не публикует.

### 1.7. Хронология: первый проход от начала к концу

1. **8 октября.** Запрошена публикация приложения. Первичный ответ Codex был общим: стек и структура ещё не были подтверждены. Это создало последующие ошибки в названиях разделов и переменных.
2. **14 октября.** При настройке Supabase возникла путаница с расположением Project URL и ключа. В одном из ответов было дано несуществующее для проекта имя `VITE_SUPABASE_PUBLISHABLE_KEY`; код фактически ожидает `VITE_SUPABASE_ANON_KEY`.
3. В импорте Vercel был выбран корневой проект Vite, а не обнаруженный внутренний Next.js-проект `apps/web`.
4. Первый деплой Vercel собрался с предупреждениями о диапазоне Node.js и устаревшей настройке `inlineDynamicImports`.
5. Публичная страница `/s/graphite/` не открылась. Сначала была ошибка `Invalid path specified in request URL`, затем `TypeError: Failed to fetch`.
6. В Supabase был зафиксирован запрос с двойным путём `/rest/v1/rest/v1/rpc/public_tenant_bootstrap`. После изменения/повторного деплоя браузерная диагностика уже показывала правильный путь `/rest/v1/rpc/public_tenant_bootstrap`, но соединение со старым проектом Supabase закрывалось с `ERR_CONNECTION_CLOSED`.
7. Перезапуск проекта не помог. Причина сбоя старого проекта не была доказана. Был создан новый проект Supabase как обходной путь.
8. **19 октября.** Команда `supabase link` сначала была запущена с буквальным заполнителем `NEW_PROJECT_REF` и закономерно завершилась ошибкой.
9. Несколько запусков `supabase db push` завершались ошибками временной роли, пароля, pooler-соединения и IPv6. После сетевых действий, точный состав которых в истории не зафиксирован, команда завершилась `Remote database is up to date`.
10. При развёртывании функций одна команда была склеена в имя `public-apinpx`; затем загрузка Docker-образа Edge Runtime несколько раз оборвалась с EOF. Позже все четыре функции успешно развернулись.
11. После переключения Vercel на новый Supabase страница сообщила, что студия не найдена или не опубликована. Миграции и функции не создавали опубликованный экземпляр `graphite`; потребовался `tenant:publish`.
12. Публикация остановилась на запрете MIME-типа `application/manifest+json`. Разрешённые MIME-типы Storage были вручную расширены, после чего пользователь подтвердил успешную публикацию.
13. Глубокий маршрут выбора услуги дал Vercel 404, потому что проект генерировал `_redirects` для Cloudflare Pages, а Vercel его не использовал. Коммит `9fe2d3d` добавил `vercel.json` с переписыванием SPA-маршрутов.
14. Свободное время не загружалось. Сначала был добавлен production-origin, но пользователь открыл preview-домен с другим hostname. После настройки обоих происхождений или использования production-домена поток записи продолжился.
15. Создание записи остановилось из-за отсутствия `BOOKING_TOKEN_SECRET`. После установки секрета пользователь дошёл до созданной записи.
16. Push сначала не включался из-за отсутствующего VAPID-ключа, затем кнопка бесконечно ждала Service Worker. Коммит `7a27914` перенёс регистрацию на корневой `/sw.js`. После этого Brave вернул `Registration failed - push service error`; после настройки браузера или использования другого браузера пользователь сообщил: «всё работает».
17. Для кабинета владельца выяснилось, что пользователь не хочет Auth в демонстрационной версии. Был выбран `VITE_DEMO_MODE=true`, который обходит вход, но переводит не только кабинет, а весь репозиторий данных в локальный режим браузера.

### 1.8. Обратный проход: от результата к первопричинам

Обратная проверка выявила проблемы, которые не были очевидны в момент исправлений:

- Успех push-кнопки не доказывает доставку уведомлений: `notification-dispatch` требует `CRON_SECRET`, VAPID-секреты и установленное расписание. Подтверждения последним двум этапам нет.
- Ручное добавление MIME-типов исправило новый проект, но исходная миграция всё ещё не разрешает `application/manifest+json` и `application/json`; новый проект повторит ошибку.
- `VITE_DEMO_MODE` имеет значение по умолчанию `true`. Если переменная отсутствует или намеренно включена ради входа владельца без пароля, реальные записи перестают быть общими и сохраняются в браузере.
- Ошибка Vercel 404 была не просто отсутствующим правилом: документация и сценарий сборки изначально ориентированы на Cloudflare Pages, поэтому несоответствие платформы системное.
- Современная документация Vercel не подтверждает историческое утверждение Codex, что тип переменной `Secret` мешает Vite получить её при сборке. Это было ошибочное направление расследования.
- Современная документация Supabase указывает, что изменение function secret применяется без повторного развёртывания функции. Повторные `functions deploy` после `secrets set` были лишними.
- В корне репозитория остался незарегистрированный пустой файл `npx`; его происхождение напрямую не доказано, но время и имя согласуются с ошибочно склеенной командой.
- В переписке были опубликованы пароль БД и service-role ключ. Подтверждения их ротации нет.

## 3. Подробный разбор каждой ошибки

### ERR-001 — Неточная навигация Supabase и неверное имя переменной

**Категория:** Configuration / Supabase / Codex.

## 6. Универсальные выводы

### 6.1. Причины, вызвавшие больше всего сбоев

1. **Несогласованная конфигурация между клиентом, Supabase и Vercel.** URL, exact origin, server secrets, VAPID и demo flag распределены между разными системами.
2. **Отсутствие полного release pipeline.** Schema, functions, tenant content, frontend, CORS, Auth и cron развёртывались отдельными ручными шагами.
3. **Несоответствие целевой платформы документации.** Репозиторий был подготовлен под Cloudflare Pages, а фактический hosting — Vercel.
4. **Диагностика по предположениям.** Тип Vercel Secret, pause state и build warnings объявлялись возможными причинами без проверки и отвлекали от сетевых запросов и исходного кода.
5. **Недостаточная end-to-end проверка.** Успешный build, deploy функций или push subscription принимались за готовность всей пользовательской функции.

### 6.2. Что можно было предотвратить заранее

- Неверное имя переменной и двойной REST path — статической проверкой env-контракта.
- Literal placeholder — валидацией project ref.
- MIME-ошибку — контрактным тестом publisher ↔ bucket policy.
- Vercel 404 — прямым запросом глубокого URL после deploy.
- CORS — OPTIONS-тестами для production и preview origins.
- Отсутствующие booking/VAPID/cron secrets — manifest обязательных server secrets.
- Service Worker hang — health-check регистрации с тайм-аутом.
- Утечку секретов — автоматическим scanner и шаблонами команд без значений.
- Переключение приложения в localStorage — запретом demo mode для production.

### 6.3. Что чаще всего повторялось
